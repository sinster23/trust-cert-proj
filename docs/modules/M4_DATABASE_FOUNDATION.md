# M4 — Database Foundation

**Project:** Credence  
**Assignment:** Phase 1A — Shared Database Foundation  
**Owner:** Member 4  
**Status:** Ready for implementation

## 1. Objective

Build a reusable MongoDB database layer for Credence.

The immediate purpose is to support the upcoming Authentication module (M1). This assignment does **not** include certificate creation or certificate verification.

By the end of this task, other modules must be able to store and retrieve user records without writing MongoDB queries themselves.

## 2. Technology

- Python and FastAPI
- MongoDB Atlas or local MongoDB
- PyMongo Async (`AsyncMongoClient`)
- Pydantic for data validation
- Pytest for testing

Use the asynchronous PyMongo API. Do not use Motor.

Place placeholders in `backend/.env.example`.

Do not commit a real `.env` file or an actual Atlas connection string.

Use a dedicated database for automated tests, such as `Credence_test`. Tests must never run against the shared development database.

## 6. Connection management

Implement a shared asynchronous MongoDB client.

Requirements:

- Use `AsyncMongoClient` from `pymongo`.
- Initialize the connection during FastAPI startup.
- Confirm connectivity using a database ping.
- Make the database accessible to repository code.
- Close the client during application shutdown.
- Do not create a new MongoDB client for every request.
- Handle connection failures without exposing credentials or connection strings.

Use FastAPI's lifespan mechanism for startup and shutdown.

## 7. Initial user data model

The initial `users` collection contains:

| Field | Type | Notes |
|---|---|---|
| `_id` | MongoDB ObjectId | Generated by MongoDB |
| `email` | String | Required, normalized, unique |
| `password_hash` | String | Required; never store plaintext passwords |
| `is_active` | Boolean | Defaults to `true` |
| `created_at` | UTC datetime | Set when created |
| `updated_at` | UTC datetime | Set when created; updated when changed |

**Do not add roles or permissions yet.** M2 will define those requirements later.

Normalize email consistently before storage and lookup—for this MVP, trim surrounding whitespace and lowercase the email. Do not silently alter other user fields.

Create a unique index on `users.email`. The index, rather than a separate “check first” query, must enforce uniqueness even when requests arrive concurrently.

## 8. User repository contract

Implement a `UserRepository` exposing these asynchronous operations:

```python
async def create_user(
    email: str,
    password_hash: str,
) -> UserRecord:
    ...

async def get_user_by_email(
    email: str,
) -> UserRecord | None:
    ...

async def get_user_by_id(
    user_id: str,
) -> UserRecord | None:
    ...
```

`UserRecord` is the internal user representation. It contains the fields listed in Section 7. It is **not** an API response model and must not be returned directly to frontend clients because it contains `password_hash`.

Expected behavior:

- `create_user` stores the supplied password **hash**; it does not hash passwords itself.
- `get_user_by_email` returns the matching user or `None`.
- `get_user_by_id` returns the matching user or `None`.
- Invalid user IDs return `None` or a documented controlled error; they must not cause an unhandled exception.
- Duplicate emails raise a documented `DuplicateUserError`.
- Unexpected database failures raise a controlled database exception without exposing secrets.
- Repository methods must not return raw MongoDB driver documents to M1.

Define and document the exact `UserRecord` type and exception names in the implementation. Keep the three method signatures above stable so M1 can build against them.

## 9. Security requirements

The member must ensure:

- Database credentials are read from environment configuration.
- The frontend never connects directly to MongoDB.
- The MongoDB account has only the permissions needed for development.
- Passwords are stored only as hashes supplied by M1.
- User inputs are validated before persistence.
- MongoDB errors and connection strings are not returned in API responses.
- Email uniqueness is enforced at database level.
- Automated tests use a separate database.
- No credentials, private keys, or production-like secrets appear in commits or logs.

For Atlas, do not make the database publicly accessible to everyone merely to simplify team development. Configure network access for the team’s development environment.

## 10. Testing requirements

Write tests covering:

- Successful database connection and clean shutdown.
- User creation.
- Retrieval by email.
- Retrieval by ID.
- Missing user returns `None`.
- Duplicate email is rejected.
- Email normalization works consistently.
- Stored record contains `password_hash`, not a plaintext `password` field.
- Invalid user ID is handled.
- Database failure is translated into a controlled exception.
- Test data is isolated from the development database.

Tests must clean up their own data. Never delete the shared development database as part of test setup or teardown.

## 11. Out of scope

Do **not** implement:

- Registration or login endpoints
- JWT generation or validation
- Password hashing or password verification
- Roles or permissions
- Certificate creation or storage
- Digital signatures or cryptographic signing keys
- Certificate verification
- AI-based analysis
- Frontend screens

Those belong to other assignments or later phases.
